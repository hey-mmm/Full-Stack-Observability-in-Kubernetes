## Root cause of the previous 32 PASS / 1 FAIL

Failing check: "HTTP through DNS and ClusterIP Service from master Pod to worker Pod".
The failure was hidden by `2>/dev/null` in the retry loop. Reproducing with a
preserved namespace exposed the real wget stderr:

    Connecting to netcheck.observability-acceptance-65851.svc.cluster.local:8080 (198.18.0.190:8080)
    wget: error getting response

198.18.0.190 is not a cluster address. The Service itself was healthy:

- Service selector netcheck-role=worker, ClusterIP 10.103.25.73.
- EndpointSlice netcheck-hvvwm: 10.244.171.67:8080, ready=true, serving=true.
- Worker Pod httpd listening on :8080; wget from the worker Pod to 127.0.0.1:8080 returned network-ok.
- master -> worker Pod IP HTTP (http://10.244.171.67:8080) returned network-ok.
- master -> Service ClusterIP HTTP (http://10.103.25.73:8080) returned network-ok.
- `nslookup netcheck.<ns>.svc.cluster.local` from the master Pod returned 10.103.25.73.
- kube-proxy ConfigMap mode is empty (default) and the pod logs "Using iptables Proxier";
  the KUBE-SEP rule for this Service DNATs to 10.244.171.67:8080. No proxy/nft defect.

The divergence is in name resolution. Pod /etc/resolv.conf inherited the node
search domain:

    search <ns>.svc.cluster.local svc.cluster.local cluster.local localdomain
    nameserver 10.96.0.10
    options ndots:5

Because the fully qualified name has 4 dots (< ndots:5), glibc tries the search
suffixes first, including:

    netcheck.<ns>.svc.cluster.local.localdomain

That name leaves the cluster.local zone, so CoreDNS forwards it to the node
upstream 11.0.1.2, a fake-IP/proxy resolver that answers non-existent names
with an address instead of NXDOMAIN. The bogus answer won before the absolute
name was tried:

    nslookup netcheck.<ns>.svc.cluster.local.localdomain  -> 198.18.0.190
    nslookup netcheck.<ns>.svc.cluster.local              -> 10.103.25.73
    wget http://netcheck.<ns>.svc.cluster.local.:8080     -> 10.103.25.73, network-ok

This broke any in-cluster FQDN lookup with fewer than 5 dots, not just the test.

## Fix applied (Ansible reproducible)

Removed the stale `localdomain` search domain from /etc/resolv.conf on master and
worker (backup /etc/resolv.conf.bak-pre-localdomain-fix). systemd-resolved
regenerates /run/systemd/resolve/resolv.conf, which kubelet uses
(KubeletConfiguration resolvConf), so new Pods receive only the cluster search
domains.

- ansible/roles/common/tasks/main.yml: remove the localdomain search entry,
  notify the handler, and fail if it reappears.
- ansible/roles/common/handlers/main.yml: restart systemd-resolved.

Verification after the fix, fresh Pod on master:

    search dnsfix-probe.svc.cluster.local svc.cluster.local cluster.local
    Connecting to netcheck.<ns>.svc.cluster.local:8080 (10.103.25.73:8080)
    network-ok

External resolution through the lab proxy still works. The acceptance script was
not changed (guest and repo copies have the same MD5); no namespace, taint,
iptables or cluster state outside the temporary test namespace was modified.
